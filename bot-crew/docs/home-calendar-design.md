# EverBot · 首页是一条时间轴

这份文档是「把首页做成日历」的完整设计。写法跟 `DESIGN.md` 一样：主流怎么做、我们怎么做、为什么、不做什么、落在哪。还没落地，落地后把结论并进 `DESIGN.md`，这份删掉。

---

## 0. 这一页只回答三个问题

1. **现在什么在等我？** —— 卡点、要拍板的卡。没有时间戳。
2. **接下来会自己发生什么？** —— 例行任务到点、会议、有截止的事项。有时间戳。
3. **这件事放到什么时候？** —— 唯一需要用户主动"排"的动作。

第 2、3 问决定首页是一块网格；第 1 问在网格上没有位置，所以它挂在旁边一条常驻的栏里。

## 1. 日历不是镜子，是事件模型

**主流**：agent 产品的首页是一个输入框，或者一串会话。日历是另一个 App 的事，最多做成一个只读小组件。

**我们**：首页是一条时间轴，上面跑的是**一种事件**，四个来源汇进来。日历不是"把用户日程搬过来看"，它是这个产品里**唯一能把一件事放在某个时刻**的地方——例行任务是事件，有截止的事项是事件，用户从 Outlook 同步进来的会是事件，Zoom 会议是事件。它既是视图，也是写入面。

**为什么**：agent 是在你不看的时候干活的，所以你丢掉的恰恰是对「什么时候」的掌控——这个卡点等了我三小时、周报明早八点会发出去、九点那个巡检还在跑。这些今天散落在各个 bot 的设置和对话里，全局没有一根时间轴能看见。

## 2. 一个事件类型

```ts
interface CrewEvent {
  id: string;
  title: string;
  start: number;
  end?: number;              // 缺失 = 时刻型（例行任务触发点、截止时刻）
  allDay?: boolean;
  /** 谁是这条事件的权威。crew = 我们自己的，改它就是改源；cal/meeting = 外部的，只读 */
  source: 'crew' | 'cal' | 'meeting';
  /** crew 源指回真源，事件本身不是真源 */
  ref?: { kind: 'routine' | 'todo' | 'matter'; botId?: string; id: string };
  /** 外部源的身份，用于幂等同步 */
  extern?: { account: string; calendarId: string; uid: string; etag?: string };
  /** 谁到场、来做什么。整套设计里最重要的一个字段 */
  actor?: { botId: string; act: 'run' | 'attend' | 'prepare' | 'followup' };
  /** 到场的前置条件，不满足要提前说，不能到点了才失败 */
  needs?: ('computer' | 'login' | 'mic')[];
  recur?: Recur;             // 结构化。中文串「每天 20:30」只是它的显示形式
  state: 'planned' | 'running' | 'done' | 'missed' | 'blocked';
  join?: { app: 'zoom' | 'feishu' | 'tencent' | 'teams' | 'meet'; url: string };
}
```

真正要紧的只有两个字段：**`actor`（谁执行）** 和 **`needs`（到不了场的原因）**。其余都是显示。

**外部事件不进我们的库当真源**，只按窗口缓存（`uid` + `etag`）。我们的库只存 `crew` 源，以及"我们给外部事件加的东西"（`actor`、我们的笔记），用 `uid` 挂上去。这样同步幂等，外部删了也不留孤儿。

## 3. 四个来源

| 来源 | 今天有没有 | 事件长什么样 | bot 的价值 |
| --- | --- | --- | --- |
| **例行任务** `Routine` | **已经在跑** | 时刻型，`actor.act='run'` | 就是它自己 |
| **bot 排的日程** `CrewEvent` | **已经能排** | 时刻型或区间型，`who` 说明谁做 | 它自己判断你需要一个日程 |
| **有截止的事项** | 事项有，截止没有 | 时刻型，`actor` = 负责的 bot | 到点前提醒/自己动手 |
| **用户日程**（Outlook / Google / 飞书日历） | 连接器已有，没接进来 | 区间型，`source='cal'` | 会前准备、撞车、会后跟进 |
| **会议**（Zoom / 飞书会议 / 腾讯会议） | 没有 | 区间型 + `join` | **bot 到场** |

例行任务这条要特别说：`crew-server/src/scheduler.ts` 已经在每 20 秒 tick，按 `settings.timezone` 解析「每天 20:30 / 工作日 18:00 / 每周一 09:00 / 每 30 分钟」，到点给 bot 发 `kind:'routine'` 的消息。但它们只出现在每个 bot 自己的设置和右侧面板里，**没有任何地方能看到全体的下一次触发**。首页第一版就是把这件已经在跑的事显出来，不需要任何新连接器。

**会议识别**：join 信息在标题、地点、正文、`onlineMeeting` 字段任何一处都可能出现（实测有事件的标题整个就是一条 zoom URL）。所以要一个多处扫的抽取器，认出来之后**重写标题**：标题是 URL 时显示成「Zoom 会议 · 参与人」，不在日历上铺一串 URL。

## 4. 动线：首页就是「日程」，今天是其中一列

**主流**：日历默认周/日网格，因为它服务的是"我的时间被占掉多少"。

**我们**：首页是**日程**——一周的网格。名字不叫「周」：它同时容得下用户的会和 bot 到点自己动，以后接 Google / 飞书日历时词也是通的。曾经想过让「今天」做落地页、周只做排期面（一条列表回答"现在什么在等我"，网格回答"哪天有空"），2026-09-10 定的是**不做今天视图**：一个产品不需要两个入口回答同一件事，「今天」就是网格里高亮的那一列。

代价要认：「什么在等我」在网格上没有位置——卡点和要拍板的卡没有时间戳。所以日程右边挂一条常驻的**等你**栏，卡点排最前，每条写**等了多久**（这是唯一的紧迫感来源）；窗口窄到 1120px 以下先收掉它，七列挤到 50px 什么都读不出来。

- **月**：不做。真要做也只做密度和全天里程碑，不做格子里塞事件。
- **日网格**：不做。它是一周那张网格的低密度版本，只多了"空白的形状"，而那个价值在周视图里更强；窄屏下周退化成一列，不是退化成日视图。

**为什么网格而不是列表**：一旦要**放**东西——会前准备放哪、这周哪天有空让 bot 做那份报告——列表答不了"哪里是空的"。空白是网格独有的信息。

## 4b. 点开一件事，先看到一张卡

**主流**：日历上点一格，要么直接进编辑态，要么弹一个把所有字段摊开的详情面板。

**我们**：先给一张卡，卡不是编辑器。**一张卡三段**，来源不同只换中间那一段：

1. **是什么** —— 标题、这一次的时刻、它从哪来（例行 / 事项 / 某本日历）
2. **归谁** —— 哪个 bot，以及它在这件事上做什么（点进去就是它的对话）
3. **能做什么** —— 一两个动作，外加一条回到真源的路：例行是那张例行任务表单，事项是对话，外部事件是它自己的日历

三条规矩：

- **状态是主角。** 没跑、卡住、到不了场都用警告色，并且**把能救它的那个动作放到主位**——例行没跑，主按钮是「立刻跑一次」；写法后台不认，主按钮是「改这条」；事项卡住了，主按钮是「去处理」。顺利的那些不着色，不抢注意力。
- **只读的字段不给可编辑的样子。** 外部日历同步来的时间、循环、参与人是纯文本；只有我们自己加在它上面的那半（谁到场、到场做什么）才是控件，用一条分割线隔开。
- **用不上的字段不留位置。** 例行不谈参与人，会议不谈「结果发到哪」，没有时刻的常驻型不画时间行。

每种来源上这张卡带什么：

| 来源 | 中间那段说什么 | 主位动作 | 真源 |
| --- | --- | --- | --- |
| **例行任务** | 何时（`每天 08:14`，按用户的语言说）、结果发到哪几处 | 没跑 → 立刻跑一次；写法不认 → 改这条 | 那条例行任务自己的页面 |
| **bot 事项** | 这个时间是**截止**还是**打算做的时刻**（必须说清是哪一种）、属于哪个事项、卡在哪 + 等了多久 | 卡住了 → 去处理 | 对话（定位到那条消息） |
| **三方会议** | 循环、参与人、会议链接（只读）＋ 谁到场、到场做什么、到场前提三行（可写） | 到不了场 → 去把电脑开着 / 改成会后看纪要 | 源日历（改时间得去那边改） |

**为什么不直接跳走**：日程是一张地图，点一个点应该先告诉你这是什么、归谁、要不要管，而不是把你扔进一段对话里再自己找。跳转是卡上的一个动作，不是点击的默认结果。

## 5. bot 到场，是这套东西的终点

会议同步进来的终点不是日历上多一行，是到点了 bot 用**那台共用电脑**（Chrome + CDP + `operate`，见 `DESIGN.md` 第 9 条）自己点进会议链接，坐在里面记录，散会出纪要和待办——而待办又变成新的事件。这个闭环别人做不了，因为别人没有一台常在的电脑。

- **前置检查提前做**，不是到点才失败：开会前 N 分钟核一遍电脑在不在、登录态还有没有、join 链接能不能打开；不满足就**提前发卡**说明。这跟 `extensions/recover.ts` 是同一个思路——能修就修，修不了才交回给人。
- **第一版只能静默旁听**：云机器的 Linux 桌面能开网页版会议，但没有麦克风和摄像头（`needs` 里的 `mic` 就是标这个）。事件上必须标出来，不能让用户以为 bot 到场了其实只是个黑框。
- **本机 `moved` 模式下电脑关机 = 到不了场**。这类事件排进去的时候就要标，不要等到点了才说。
- 用户自己在场的会、bot 到场的会，视觉上必须一眼分开。

## 6. 时区和循环

- **时区只有一个来源**：`settings.timezone`，`scheduler.ts` 已经在用它（曾经踩过云机器 UTC 把「每天 20:00」跑成北京时间 04:00）。日历不许自己取浏览器时区。
- **循环内部存结构**，中文串是 format 出来的显示形式。外部 RRULE 转得进来的就转，转不进来的（复杂 `BYSETPOS`、例外实例一堆）当"只读、按实例展开"，不试图往回还原成规则。**不要让 RRULE 反向污染 `Routine`**——现在这个中文串很好，可读、模型会写。
- **只在窗口内展开**（当前视图 ±1 周），不预生成实例，不落盘。

## 7. 写入边界

第一版：**外部日历只读入，我们只写自己的事件。**

不给用户的真日历发邀请、改时间、回复出席。理由：改别人的日历是不可逆的对外动作，还会撞上会议邀请的回执语义（你截图里那些虚线框就是"未响应"）。什么时候开：等 bot 建的事件被采纳率稳了，并且有一张明确的确认卡再说。

**要同步哪些日历得让用户挑**，不能全同步——你的账号下就有「我的日历 / 生日 / 中国节假日 / 其他日历 / 用户日历 / 组」，节假日和生日铺进时间轴纯是噪音。

## 8. 不做

- 不做「今天」这个单独的视图（今天就是网格里高亮的那一列）
- 不做月网格和日网格
- 不做拖拽修改外部事件
- 不做我们自己的日历账号体系（永远只做别人日历的读端 + 我们自己事件的写端）
- 不做提醒/闹钟通道——提醒就是 bot 的一条消息，走已有的 `channels`，不新起一套
- 不在日历上显示 bot 的每一步工具调用（那是事项面板的事）
- 不把节假日/生日这类日历默认同步进来

## 9. 分期

- **P0 · 日程（已做）**：只有 `crew` 源，只读。把每个 bot 已经在跑的例行任务按本机时区展开到一周的格子上，右栏挂「等你」并给出等待时长，落地页改成它；点一条先出事件卡（例行那一种已经做了，另外两种等来源接进来）。零新连接器——纯粹把已经在跑、却只藏在各个 bot 设置里的东西显出来。
- **P1a · 模型能排（已做）**：bot 有一个 `schedule` 工具——用户说了具体时间的事（「下周三提醒我交报告」），或者它自己判断出用户会需要一个日程，就排上一条。到点了 scheduler 把这条连同它当时写的 note 交回给排它的 bot，由 bot 决定说什么、做什么：**提醒就是它的一条消息，不另起一套通知通道**（第 8 条）。只发生一次的归 `schedule`，反复的仍然是例行任务。
- **P1b · 用户能拖**：拖拽给事项定截止、空白处自己新建一条、在网格上拖一条例行任务等于改它的 `schedule`。
- **P2 · 接一个外部日历**：先 Outlook（用户自己在用），只读入 + 日历挑选 + join 抽取 + 标题美化。
- **P3 · bot 到场**：前置检查 → 用共用电脑进会 → 纪要 → 待办回流成事件。

## 10. 落在哪

**P0 已经落地的**，全在前端——例行任务本来就在客户端的 state 里，服务端一行没动：

- `bot-crew/src/calendar.ts`：把 `每天 20:30 / 工作日 18:00 / 每周一 09:00 / 每 N 分钟 / 每小时` 解析成 cadence，算出某一天的触发时刻，和显示窗口。写法和后端 `crew-server/src/scheduler.ts` 的 `lastDue` 是同一套，**改一处要改两处**；差别是这段跑在浏览器里，本来就是用户的时区，所以不做时区换算。
- `bot-crew/src/components/Week.tsx`：网格、常驻行、现在线、右边的「等你」。
- `bot-crew/src/components/EventCard.tsx`：点开一件事看到的那张卡；上面三条规矩写在它的文件注释里。
- 服务端的日程：`crew-server/src/types.ts` 的 `CrewEvent`（存在 `store.data.events`，不长在 bot 身上——它不是 bot 的属性，是时间轴上的一条）、`extensions/schedule.ts`（模型的工具：add / list / move / drop）、`scheduler.ts` 的 `fireEvent`（到点交回给排它的 bot，迟到了如实说迟了多久，由它判断还值不值得说）。
- `bot-crew/src/utils.ts` 的 `waited()`：等待时长只给一个量级。
- `styles.css` 的 `.week / .wk-*` 段；`types.ts` 的 `Selection` 多一个 `'week'`；`App.tsx` 路由；`Sidebar.tsx` 多一个 pill；`ws-agent.ts` 里新装的落地页。

P0 定下来的几条小规矩：

- **进不了格子的东西要看得见。** 常驻型（每 30 分钟这种）一天跑几十次，铺进格子只剩噪音，所以它们和**后台压根不认的写法**（`出行前一天 18:00`、`每月 1 日` 这类 `lastDue` 返回 undefined、因此永远不会被触发的）一起放在网格上方一行；不认的那些是警告色。这一屏顺手暴露了「写了但永远不会跑」的例行任务。
- **只说 `lastRun` 能证明的话。** `lastRun` 只记得最后一次跑，所以格子只敢分三种：还没到点、到点了之后再没跑过（警告色，这才是要看的）、以及过去（一律当跑过了，不替它编细节）。
- **窗口跟着数据走。** 默认 7:00–22:00，有任务或者「现在」落在窗口外就把窗口撑开——不能有东西藏在格子外面。
- **时区角上只写 `GMT+8`**，完整的 `Asia/Shanghai` 放不下。

**后面几步预计落在**：服务端新 `crew-server/src/calendar.ts`（事件聚合、窗口展开、外部同步缓存、join 抽取）、`store.ts` 加 `events`（只存 crew 源和外部事件的附着物）；外部日历走已有的 MCP 层（`googlecalendar` / `outlook` / `lark-mcp` 的 calendar 范围），不新写连接器。
