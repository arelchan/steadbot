# Steadbot · 设计理念与特色设计

这份文档分两部分。第一部分是我们对「下一代 agent 产品长什么样」的几个判断；第二部分是每个判断落下来的特色设计——怎么做（具体逻辑）、为什么、落在代码哪里。主流做法只在需要对照时提一句。

维护规则：判断改了先改第一部分，再看第二部分哪些设计站不住；新的形态决定落地时归到某个判断底下加一条；改了主意就改原文，不留「曾经」。实现细节不写在这里，写在各包的 README 和代码注释里。

---

# 一、设计理念

**1. 与 agent 的对话以异步委托为主，不是同步问答。** 值得交给 agent 的事大多不是三秒能答完的。产品要为「交代完去干别的」设计，而不是为「看着它打字」设计。由此要解决三件事：委托要有凭证（事项），改主意要立刻生效（插话），什么时候来找用户是 bot 的判断而不是设置项。

**2. 最贴近用户理解的产品形态就是通信软件。** 用户会用微信、飞书，就会用 Steadbot：左栏是人，点开是一条聊天，@ 谁、拉谁进群、在哪个 IM 里说话，都不需要学。用户面对的是「同事」，不是「系统」——所以没有会话、没有 prompt、没有工具开关，界面也不解释自己。

**3. 所有配置由 bot 自己完成，包括接 IM。** 用户知道要办什么事，不知道要什么 prompt、哪个 key、装什么包。配置是 bot 该学会的能力，不是交给用户的作业：bot 从一句话里推出自己的人设和职责，用 `build` 改自己，用电脑去平台后台把自己接进飞书，机器自己把依赖装齐，版本自己升。

**4. GUI 是未来。** 当模型能看懂桌面、操控电脑，人类几十年沉淀下来的软件——设计器、剪辑、3D、ERP 后台——全部对 agent 开放，不需要每个软件先出一个 API。所以 bot 有自己的电脑，用户能看到屏幕直播；普通网页走文字快照，画板、拖拽、桌面软件走一个能看屏幕的模型；一句「把这三个图层对齐导出」丢出去，用户可以先去干别的。

**5. bot 住在常开的机器上，登录态属于用户的设备。** bot 要能在你睡觉时干活，所以得住在常开的地方；但账号登录态是设备的，不搬上云、不烤进镜像，云上的 bot 借用本机的，本机关机就借不到，接受这个代价。

**6. 我们做框架，不做垂直功能。** 剪视频、做美术、做 PPT 一个框架不可能都做好，开源社区有的是 skill 和 MCP。我们做的是让 bot 能发现、装配、验证、沉淀：一条池、一个自我改造的门（`build`）、两轨记忆。垂直能力进池，不进代码。

# 二、特色设计

## 理念 1 · 异步委托

### 1.1 一切先落成事项

**怎么做**：bot 收到每条消息，先判断是新建、更新还是关闭哪个事项，落了再回；干活在后台，进度写在事项上；要用户拍板时发一张卡（确认 / 选择 / 卡住），用户什么时候有空什么时候点。事项面板常驻在对话右侧，不需要 bot 播报。

事项只有四态——**进行中 / 待确认 / 已完成 / 已关闭**（`doing / waiting / done / closed`），因为这四个就是用户在日程右栏看到的四叠：状态机和汇报是同一件事，多出来的状态没有地方显示，也就没人维护。原来还有 `open` 和 `blocked`：前者对用户和「进行中」没区别——bot 接下了就是在做；后者对用户和「待确认」没区别——都是不理它就停在这，界面里这两个本来就一直成对出现。「卡住了」那份紧迫感由卡片的种类表达，不靠事项状态。做成了用 `close` 并写结果，不做了（取消、过期、重复、做不了）用 `drop` 并写原因——这两叠在用户那边是分开的，不能拿一个 done 糊过去。

只有 `todo` 工具能建事项，标题是模型写的一句人话。@ 只负责把话转达过去，是不是活由收到的人判断——被点名、道谢、同步进度都不建。牵头人派活走 `todo(create, assignee=某人, brief=交代清楚)`，事项直接建在对方名下，`brief` 是对方唯一看得到的交代。事项归谁、属于哪个群、谁交办的、用户从哪个入口说的，由运行时按这一轮的来路快照进 `TodoOrigin`，模型指定不了也伪造不了，所以事项上才能长出「飞书」「@架构大师 交办」「例行」这类标签。

例行任务是委托的定时版：一条时间表（每天 / 工作日 / 每周几 / 每小时 / 每 N 分钟）加一句指令，到点由运行时替用户说一句话；结果发到哪几个出口（App 和它接了的 IM）由用户勾选。新建或改了时间的例行从「当下」开始算，下午建的「每天 09:00」等明天，不立刻补跑。

**为什么**：事项是委托的凭证：用户不用记得自己交代过什么，bot 也不用翻聊天记录找自己干到哪了。系统替模型记账（把「回复里出现 @」当成「交接了一件活」）的代价是看板被点名和致谢淹没，标题只能靠正则截；宁可模型偶尔漏记一条——每轮系统提示词都会把它未完成的事项列给它看。

**在哪**：`crew-server/src/extensions/todo.ts`、`ask.ts`、`act.ts`；`router.ts` 的 `crew:handoff`（转达不建事项，送不到就把那条事项标 blocked）；`types.ts` `TodoOrigin`、`Routine`；`scheduler.ts`；前端 `RightPanel.tsx`、`BotConfigModal.tsx` 的例行页。

### 1.2 随时插话，bot 立刻改主意

**怎么做**：bot 正在说话时发消息，它立刻停，半句留在屏幕上标「被打断」；下一轮先看新消息，重新判断刚才在做的哪些还成立，不补完旧方案、不重复。bot 正在跑工具时发消息，正在跑的那个让它跑完（写到一半杀掉会坏文件），同一批里还没开始的作废，新消息在下一次调模型前送到。短时间内连发的几条消息合成一轮处理（1.2 秒窗口、最长 3.5 秒），用户可以像在 IM 里一样分几条说完一件事。

**为什么**：改主意是委托里最常见的事。「等它说完旧方案再纠正」浪费的不只是时间，还有用户对 bot 的信任。技术上 pi 会把被中断的输出从模型上下文里整条丢掉，所以我们把半句引用回给模型，明确说在哪被打断。

**在哪**：`crew-server/src/bots.ts` `send()` 的 `busyHere` 分支、`cutInPrompt()`、`tool_call` 拦截钩子；`GATHER_MS`。

### 1.3 找不找用户，是 bot 自己的判断

**怎么做**：没有摘要频率、免打扰档位、按类型开关。什么值得打断用户，由 bot 按它对这个用户的了解判断；用户嫌吵或嫌它不吭声，直接跟它说，它用 `build` 把标准写进自己的工作方式。系统只提供一个总开关和每个群的开关。

**为什么**：打扰阈值是关系的一部分，不是设置项。摘要和档位是把「bot 不会判断」这个缺陷制度化。我们赌 bot 能学会，并把纠正的成本压到一句话。

**在哪**：`identity.ts` 的 `REACH_OUT_RULE`；`notifier.ts` 只做「bot 说了话 → 要不要弹一下」，没有攒批。

## 理念 2 · 通信软件的形态

### 2.1 只有新 bot，没有新会话

**怎么做**：左栏是一个个 bot，每个 bot 只有一条连续的对话，从它出生那天一直往下写。要换个话题就找另一个 bot，或者新建一个。「清空聊天记录」存在，但它是和这个人「断交重来」，不是日常操作。

**为什么**：agent 的价值在于它记得你、记得手上的事。会话一开新，这段关系就归零了。一条连续对话逼着 bot 的记忆、事项、人设都长在这条线上，也逼着我们把「上下文太长」当成运行时该解决的问题（压缩、事项、记忆），而不是甩给用户。

**在哪**：`crew-server/src/types.ts` 的 `ThreadId` 只有 `bot:<id>` 和 `matter:<id>` 两种；pi 的会话文件按 bot 一份长期保留（`bots.ts` `ensure()`）。

### 2.2 多个 bot 是同事，不是子任务

**怎么做**：两条路，bot 按「结果要不要回到自己手上」选。整件事交出去、之后归对方跟用户对接，就在回复里 @它，系统转达，对方在自己那条对话里继续；要拿对方的结果接着做、或者几个人凑齐才交付得了，就 `create_group` 开一个群（一件事一个群，有牵头人和成员），结果回到同一条线上，用户随时能插一句。

群里说的话所有成员都收得到，但**只有被 @ 的人会被叫醒**：其余人拿到的是一条不触发回合的【群聊记录】，等下次轮到它说话时才读到。所以一条消息只烧一个 bot 的钱，而每个人下次开口时都知道群里发生过什么。一个群只有一个人被任务叫醒——牵头人；牵头人负责推进、派活（`todo(create, assignee=…)`）和汇总。建了群没人开口就是死群，所以建群本身会叫醒牵头人说第一句。

每个 bot 在飞书、企业微信等 IM 里是一个独立机器人、一套凭据；把我们的 bot 拉进一个 IM 群，这边就镜像出一个群。

**为什么**：orchestrator 拆子任务给 worker 的编排不透明，出了问题用户无从下手。同事关系用户天然会用：@谁、拉谁进群、看群里谁说了什么。群里全员广播会让一条消息引爆 N 个回合、再各自引爆 N 个，所以「都看得到、只有被叫到的才开口」是唯一能同时要透明和要成本的分法；反过来，如果同事之间什么都看不到，群就只是「@ 加一条用户能读的流水」，bot 没有理由选它——线上跑了 586 条消息、14 个 bot，bot 主动拉群 0 次，@ 转达 2 次。

**在哪**：`bots.ts` 的 `crew:handoff` 事件、`parseMentions` 与群内转播；`router.ts` `createMatter`（建群即叫醒牵头人）；`index.ts` `createGroup`（任务只叫醒牵头人）；`identity.ts` 的「团队里的其他 bot」与「当前群聊」两段；`types.ts` `Matter`；`channels.ts` 的群镜像。

### 2.3 IM 是同一段关系的不同入口

**怎么做**：飞书、企业微信、Slack、Telegram 发来的消息和 App 里的私聊是同一条对话、同一段关系。消息正文开头带来源标记（【飞书】），回复自动送回来源；bot 说话方式不因来源变化，也不复述来源。

**为什么**：用户在哪个入口出现是他的事，bot 记住的应该是这个人。

**在哪**：`bots.ts` `sourceMark()`；`channels.ts` `deliver()`；`identity.ts` 「工作方式」第二条。

### 2.4 自主度三档，副作用只有一个口

**怎么做**：每个 bot 一个自主度：只告诉我 / 备好等我点 / 直接办。所有会改变外部世界的动作（付钱、下单、发消息、改别人日程）只走 `act`，由自主度和金额决定是直接执行还是先发确认卡；bot 不允许口头说「已办好」。外部系统里的写操作由 bot 自己判断可逆性，拿不准先问一句，绝不用写操作探测权限。

**为什么**：用户能理解的是「这个人我放多少权」，不是二十个工具各自的开关。把副作用收进一个口，审计、撤销、确认才有落点。

**在哪**：`types.ts` `Autonomy`；`identity.ts` `AUTONOMY_RULES`；`extensions/act.ts`。

### 2.5 界面不解释自己

**怎么做**：没有劝导句、没有「你可以……」的说明小字，空状态两三个字；二级页面是「列表 + 详情」，能选的不让人打字（例行的时间表是下拉加时间，不是自由文本）；右侧只有一个面板，身份打开时借事项的位置，关掉就还回去；弹窗一律 portal 到 body。设置里的语言是 App 的语言，十种，按浏览器语言自动选，日期时间跟着走；bot 说什么语言是另一项：默认跟界面，也可以「跟我说的」。

**为什么**：解释性文案是设计没做完的标志，也是「AI 味」的主要来源。通信软件没有人读说明书。

**在哪**：`bot-crew/src/i18n/locales/zh.ts` 是文案的源头；`Thread.tsx` `PanelToggles`；`components/Field.tsx`（一行一条的 `Row` / `Pick`）；`identity.ts` `LANGUAGE_RULE`。

## 理念 3 · bot 自己配置自己

### 3.1 一句话生出 bot，bot 自己长大

**怎么做**：在输入框说一句要办的事，bot 就出生了：名字、简介、职责、人设、头像，从这句话加上它出生的处境（团队里已经有谁、关于用户已知的、这台机器接了什么、界面用什么语言）一次写出来——没有模版，也没有一份填空骨架，所以两个相近的需求不会生出两个同一个模子里的 bot。用户等的就是这一次调用：身份一落地它就开始办事，找手册、接服务、装依赖都在第一轮的旁边进行，不排在它前面。之后它自己改自己：用户纠正了语气、同类任务反复出现却没手册、职责和现实对不上，它用 `build` 改人设、工作方式、技能手册、外部连接、例行任务，在后台进行，每次成长在对话里留一条记录。`build` 是唯一的自我改造门——记忆里攒出的新做法也走这条路排一次 build，能看见、能改、能回滚。

**为什么**：建 agent 要填表（名字、system prompt、工具勾选、模型参数）的前提是用户知道要什么 prompt；用户只知道要什么事。

**在哪**：`crew-server/src/index.ts` `createBotFromBrief()`、`infer-bot.ts`；`extensions/build.ts`；`builder.ts`；`types.ts` 的 `GrowthEvent`；前端 `Thread.tsx` 的 `born` / `evolved` 通告。

### 3.2 接 IM 由 bot 自己去后台点出来，凭据不经模型

**怎么做**：bot 要接飞书 / Slack / 企业微信 / Discord / WhatsApp，首选用共用电脑打开对方平台的后台，自己建机器人、开权限、订事件，走到凭据页用 `harvest(take, field=App Secret)` 让服务端从页面上读进配置——模型只见遮罩后的回显，任何出站正文里出现已知密钥一律替换为 ••••。用户只在登录那一步帮一下（扫码卡 / 密码卡），绝不向用户要手机号、短信验证码、App 内登录码。电脑不可用、或平台没有独立后台（Telegram 的 @BotFather）才发凭据卡让用户填。

模型、密钥、连接器凭据内置在产品里，用户界面上没有这些项；bot 要接外部服务时发授权卡走 OAuth，不向用户要凭据。

**为什么**：填 key 的人不是我们的用户。一个能端到端操作浏览器的 bot 没有理由再让用户抄一遍密钥，但模型不可信，所以读取和落盘都在它看不见的地方完成。

**在哪**：`builtin-skills.ts` 的「IM 渠道接入」两条路线；`extensions/harvest.ts`、`secrets.ts`、`extensions/connect.ts`；`~/.crew/config.json`（600 权限，只在服务端读）；`crew-server/README.md` 「配置」一节。

### 3.3 依赖不展示，机器自己收敛

**怎么做**：任何东西进到这台机器上（挂一份手册、写一份自己的手册、接一个 MCP 服务），系统就从它身上读出要装什么，合成这台机器的「想要集合」，后台一个串行的工人把机器收敛过去。界面上没有依赖这件事，也没有「补齐」按钮。用的时候只问一句「到位没有」，没到位就等一小会儿（实测 PyYAML 6s、python-pptx 7s、playwright 8s，pandas 70s），超过预算才把「正在装 X」交回给 bot 让它先做别的。想要集合是算出来的、不存盘：新机器、重建的容器、搬回本地，各自重新算一遍再装。系统级的东西（LibreOffice、poppler）只在容器里补，用户自己的电脑不动。

**为什么**：把依赖做成展示，等于让用户替机器记账；bot 照着手册干到一半 import 失败，这一轮就已经废了。装在「东西到手时」而不是「用到时」，是因为绝大多数依赖是秒级的，提前装几乎不花代价，而失败的代价是一次交付。

**在哪**：`crew-server/src/deps.ts`（想要集合、后台收敛、`ready`/`line`）；`tools.ts`；`requires.ts`。

### 3.4 版本就是提交，升级一下就到

**怎么做**：版本 = git 提交，名字 = 提交上的标签。机器之间比的是提交，人看的是 `v0.1.0`；标签之后的提交读作 `v0.1.0+3`，所以任何一个提交都有名字。「关于」里就一行：图标、Steadbot、版本标签、提交号和仓库，有新版本时右边出现「升级到 v0.x.y」。bot 住在远端机器时，远端一起升级：云机器用只读部署密钥自己拉代码，代码改动只重启，Dockerfile 变了才重建镜像，部署前等 bot 空闲。

**发一版**：`git tag -a vX.Y.Z -m '…' && git push --follow-tags`，同时把两个 `package.json` 的 `version` 改成 `X.Y.Z`——标签是给人看的名字，package.json 是没有 git 时（容器里）的兜底，两个错开就会自相矛盾。

**在哪**：`crew-server/src/version.ts`（`versionName`：本地 `git describe` 先答，本地没有的标签再问远端）、`upgrade.ts`（`waitIdle`）；前端 `SettingsModal.tsx` 「关于」。

## 理念 4 · GUI 是未来

### 4.1 bot 有自己的电脑，用户看得见

**怎么做**：云机器上有一台电脑（Xvnc 桌面 + 一个 Chrome + 一个登录态），所有 bot 共用：每个 bot 一个 Playwright MCP 进程挂同一 CDP，各在自己的标签页里干活，不加锁；屏幕在每个工作区显示同一块，用户在 App 里看直播。没有开关机概念：卡片常显屏幕，闲置 30 分钟休眠、留最后一帧，打开就唤醒；用户和 bot 可以同时操作，没有「接管」，分辨率跟随窗口。

**为什么**：agent 用电脑干活时用户想看，而且经常要帮它一把（登录、验证码）。电脑是团队的工作站，登录一次全员可用；每 bot 一台既浪费内存也让登录态碎在各处。

**在哪**：`crew-server/src/desktop.ts`（Xvnc + noVNC + Playwright、`readPage`）；`types.ts` `Desktop`；前端桌面卡片。

### 4.2 两种手：文字快照走 Playwright，复杂界面交给 `operate`

**怎么做**：普通网页走 Playwright 文字快照，便宜、准，bot 自己一步步点。画板、设计器、剪辑、3D、拖拽、桌面软件、产品里的长流程交给 `operate(goal, context)`：bot 把一个完整的小目标整体交出去（「把这三个图层对齐并导出 PNG 到桌面」），由一个能看屏幕的模型（`guiModel`，留给 GPT-6 一类 computer-use 模型）看截图、出一个动作、执行、再看，做完回一段话和最后一张截图。动作词汇对标 OpenAI computer use（click / double_click / move / scroll / type / keypress / drag / wait / screenshot），云机器走共用电脑的 X 显示（xdotool），Mac 本地走 screencapture + cliclick，一套循环两边通用。每步用 ImageMagick 比对前后截图，画面没变就告诉模型「上一步没生效」，连续三步没变即停；用户一动鼠标它就让出屏幕，等人停手再继续；需要登录、验证码、付款、不可逆删除它停下来交给用户。整块屏幕一次只给一个 bot。

从用户这边看，这就是一句异步委托：说完去干别的，事项上写着进度，想看就看屏幕直播。

**为什么**：文字快照覆盖不了 canvas 和拖拽，而通用的截图点击栈又贵又慢，所以两种手各管一段。实测同一个「打开 example.com」，视觉模型 16 步失败，GPT-6 五步一次成；excalidraw 里选工具、拖矩形、写字 10 步做完。换原生 computer-use 协议时只改「问模型要动作」那一段。

**在哪**：`crew-server/src/gui.ts` + `extensions/operate.ts`（手）；`extensions/computer.ts`（文字快照）；`config.json` 的 `guiModel`。

### 4.3 不换模型，把「看」外包

**怎么做**：主模型保持不变（便宜、快、无视觉）。图片、PDF、PPT、Word、Excel、扫描件统一进一个 `see(路径, 想知道什么)` 工具：能抽文字的抽文字，图和扫描件交给一个视觉模型描述，文件长又带问题时先压成答案。主模型自己有视觉时图片照旧直接进消息。

**为什么**：切模型等于换了这个 bot 的脑子：人设、工具习惯、成本全变，而且整轮对话都在贵模型上跑。外包一次调用就够。

**在哪**：`crew-server/src/vision.ts`、`extensions/see.ts`、`scripts/extract.py`、`office.ts`。

## 理念 5 · 常开的机器

### 5.1 bot 住在常开的机器上，你的电脑只是路牌

**怎么做**：一份数据（聊天、事项、记忆、技能、连接、密钥）随时可以整体搬到一台常开的机器上（自己的云主机，或托管云端），本机变成路牌，App 自动跟过去。本机的 agent 和登录态不搬，云上的 bot 借用本机的。

**为什么**：本地跑关机就停；全托管云，用户的登录态搬不上去。拆开：数据和 bot 住云上，登录态留设备。

**在哪**：`crew-server/src/machine.ts`、`runtime.ts`；`remote-install.ts`；`~/.crew/moved.json`；前端 `RuntimeView.tsx`。

## 理念 6 · 框架，不是功能

### 6.1 一条池：看·用·进化

**怎么做**：池只有一条：手册、外部工具（MCP 服务和走一键登录的平台是同一类，差别只在授权方式）、素材包。搜到不等于要装——`read` 手册用一次，用户纠正过或同类活反复来才 `build(add)` 长在身上；出生时不编手册，只检索。检索是词法和向量两路（同一个 bge-m3，记忆引擎也用它）融合出十来个候选，再由轻模型定夺，所以「帮我看看 PR 写得行不行」找得到 code-review。装不装只有一条标准：这是不是这个 bot 这份工作的常备本事——装上的每轮都在上下文里，是它是谁的一部分；符合的几本都装，偶尔才用一次的不装，库里没有对应的（学日语、家务）就一本都不装。装上就是进它自己的技能目录（`<botDir>/.pi/skills`）：每轮从目录里取出手册清单（名字、说明、路径）进上下文，正文等它要用时自己 read。目录是一 bot 一个，所以两个 bot 挂同一本是各自一份，谁进化谁的，名字也不会互相挤掉；只有产品自带的那几本（接 IM、接 MCP、接外部 agent）是共用的。

**为什么**：装上的东西每轮都占提示词，装配应当是有证据的进化而不是召回的副作用。垂直能力靠社区供给，我们的护城河是发现、装配、验证、沉淀这条链路。

**在哪**：`library.ts` / `extensions/library.ts`；`builtin-skills.ts`。

### 6.2 记忆分两轨，引擎接 EverOS，我们只管作用域和预算

**怎么做**：记忆引擎不自研，本机跑一个 EverOS sidecar（`127.0.0.1:5211`，只听回环，模型和密钥经环境变量注入），根目录 `$CREW_HOME/memory`——md 是真源，LanceDB 索引是可重建的派生物。记忆分两轨，分法是「归谁」而不是重要程度：**用户轨**（经历、原子事实、常驻画像、预判）owner 是用户，全员共用一份；**agent 轨**（干过的活、攒出来的做法）owner 是 botId，只属于那个 bot；团队共识是 owner 为虚拟 agent `crew` 的第三份，只有用户点「设为团队通用」才写进去。写入没有 owner 参数——引擎从每条消息的 `sender_id`+`role` 推出来；一轮结束发一次 `add`，线程静置 90 秒或事项关掉就 `flush` 切段。读取一轮两次并行 search（用户轨 hybrid 6 条，agent 轨 vector 4 条），加上内存里的常驻画像，预算 2.5s：没回来的就不注入，回答照常。新攒出来的 `agent_skill` 是唯一一个「bot 自己学到了东西」的机械信号，它排一次 build。

**记忆页**：四个同级 tab——Profile / Episode / Agent case / Agent skill，引擎原名；前两个关于用户、全员一份，后两个按 bot 归属。「列表 + 阅读栏」；Profile 整份铺开，每条可就地改、删、加——改和删是改引擎的 `user.md` 再把一句更正当用户的话写回去。atomic fact、foresight 不出现在界面上。

**为什么**：情节切分、事实抽取、画像聚类、case/skill 抽取、混合检索，EverOS 已经做完了；重写一遍只是把自己分叉出去。用户轨不按 bot 切，是因为用户是一个人——跟着 bot 切，他就得跟每个 bot 重新自我介绍一遍。agent 轨不互相打通，是因为手艺是自己练出来的，共享得是一次明确的动作。

**不做**：不做图数据库；不自己写抽取 prompt；不默认开 per-bot 的用户轨；不做记忆的可视化编辑器；不让 bot 直接读记忆库文件——它只能 `recall`，而 recall 只答它自己那份。

**引擎自己也是一个依赖，按依赖的规矩办**：整套版本写在 `crew-server/src/engine.json`——everos 自己会钉版本，但它的八个 everalgo 子包是浮动的，2026-09-10 建的镜像因此拉到了 boundary 0.3.0 + core 0.5.0，而 everos 1.1.3 还按老参数构造 `DetectionResult`，结果整整一天**每一次写入都是 500，而 `/health` 一直回 ok**。所以三条规矩：① 版本一处定义，镜像构建和用户机器上的自动安装读同一个文件，改它算「重的变更」、会重建镜像；② 健康检查检的是能不能写，启动时真发一条扔掉的消息，写不进去就判定不可用、并把引擎自己的报错打出来（一个只查进程活着的健康检查，和没有健康检查是一回事）；③ 每次启动都把这台机器的引擎对齐到 `engine.json`——没有就装（没有 uv 先装 uv），版本不对就换，已经对的时候 uv 只花 0.4 秒；后台进行、装不上就是这次没有记忆。「装了个能跑但版本不对的」正是搬家和手工装机的常态，只在缺失时才装是不够的——和 §17 的依赖是同一条原则，用户不需要知道有个 Python 服务这回事。

**已知的坑**：搬家时 md 带走、索引重建；两端的引擎版本由启动时的对齐保证一致（`engine.json` 跟着代码走），只有当目标机器跑的是更老的一版 crew-server 时，它钉的版本才会不同；情节叙事目前是英文（everalgo 的 zh 抽取 prompt 没接上），注入时说明一句「记录是英文的，照常说中文」；agent case 门槛很高（≥3 轮工具调用、bot 自己收尾、被判定「出过岔子并被纠正」），所以 agent 轨天生稀疏——只从麻烦里学；LanceDB 会因遗留 FTS 索引和未回收版本膨胀（26MB 记忆撑到 344GB），要定期 `optimize`；搬家只带 md 可行，但重建等于逐条重新嵌入，85 份 md 要跑几分钟到几十分钟，期间召回是空的。

**资料（knowledge）**：记忆的另一半，形状正好相反——记忆从对话里长出来，资料是用户交过来的文档。同一个引擎的另一条线：上传一份文件，引擎用能读版面的模型解析、切成主题树（每个主题有摘要 + 全文）、自动归到它自带的分类里，落在 `knowledge/<分类>/<标题>/`。它**没有 owner**，天生全组一份；也是唯一能真正删掉的一种（`DELETE /documents/{id}` 连主题一起删）。产品里它和记忆是同一维度的两个 tab（bot 配置里「记忆」「资料」）：一个是「知道什么」，一个是「以前怎么样」，都不是「怎么做」——那是技能手册。进资料库要用户明确的动作：面板里加一份，或者对话里说「以后按这份来」让 bot 用 `knowledge(file=…)` 归档；不自动收附件（切一份文档要一分多钟，多数附件是一次性的）。bot 用两层：每轮注入三条命中主题的摘要，要细节自己 `knowledge(topic=…)` 读全文。

**资料的坑**：引擎的 `/knowledge/search` 三种检索方式都硬要一个 rerank 服务（`_require_search_providers`）。OpenRouter 是有 rerank 的——`POST /api/v1/rerank`，`{model, query, documents}` 的形状正是引擎的 `vllm` 客户端，两个模型 `cohere/rerank-v3.5` 和 `qwen/qwen3-reranker-8b`（其余 id 一律 400 不存在）——所以 sidecar 起来时就配上它，同一把 key。兜底仍然留着：把查询切成词和二元组，在主题名和摘要上算重合度排序，没 key、没额度、模型下架时还能给出三行。切一份 30KB 文档成 25 个主题要 **109 秒**，所以上传是后台的，界面先显示「在读」；分类名是引擎自带的英文分类（Technology / Science…），主题名和摘要跟着文档语言。

**在哪**：`crew-server/src/everos.ts`（唯一出入口）；`bots.ts`（一轮的消息怎么攒、什么时候发）；`extensions/identity.ts`（三段注入）；`extensions/remember.ts`；`builder.ts` `pickupSkills`；`index.ts`（拉起、`/memory/overview`、`/memory/promote`、退出前 flush）；`Dockerfile`。
